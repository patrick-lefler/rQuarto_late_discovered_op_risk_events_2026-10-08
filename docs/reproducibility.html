Reproducibility and Limitations

This page documents how to rebuild every number on the site, and checks a few of those claims live: the tests, the environment status and the parameter staleness check re-run every time this page is rendered (it is excluded from the project-wide freeze: auto cache).

One command

From a clean clone:

Rscript -e 'renv::restore()'   # once: package versions from renv.lock
Rscript run_all.R               # simulations -> mlReserve experiment -> site in docs/

run_all.R runs run_simulations.R (replications, control study, break-even), installs the pinned mlReserve fork into an isolated library if needed and runs run_mlreserve.R, then calls quarto render.

Randomness

All randomness is seeded explicitly, so results do not depend on how many cores are used (tested). A master seed in params.yaml (master_seed) generates a seed for every stream:

Code 
derive_seed
function (master_seed, rep, scenario_index, type_index = 0L) 
{
    as.integer((master_seed + 1009 * rep + 100003 * scenario_index + 
        7919 * type_index)%%.Machine$integer.max)
}

Seeds depend on the replication number, the scenario index and the event-type index, so the same replication in different scenarios shares nothing accidentally, and the baseline and control arms of the control study share seeds on purpose (paired comparison). Bootstrap and frequency-severity simulations take a seed derived the same way.

What the tests cover:

  • Triangle construction reconciles exactly to the event-level data (counts and amounts, quarterly and annual) and never leaks undiscovered events into the observed region.
  • The generator is deterministic for a seed, rejects invalid parameters, keeps lags non-negative under the control shift, injects shock events exactly, and the control-improvement shift reduces time remaining by the stated fraction measured from the later of the shift quarter and the origin (events originating after the shift are not collapsed to lag 0).
  • The negative-binomial scenario has the same mean count as Poisson but larger variance, and the reporting threshold removes only losses below it.
  • Estimators: the in-house chain-ladder matches the package on a dense triangle, tolerates empty development columns, never throws (errors become failed), and sparse triangles are reported as failed or suspect, never as silent zeros. The Mack implementation with empty-column handling reproduces ChainLadder::MackChainLadder on a dense triangle (IBNR and standard error), runs where the package stops, and a zero bootstrap estimate is flagged suspect. Bornhuetter-Ferguson, Benktander and the benchmark development pattern are checked for coherence (shares in [0, 1], Benktander between BF and chain-ladder, pattern matches simulation).
  • Scoring and control functions are checked against hand-computed values.
  • A replication run is identical on 1 and 2 cores.

Caching and runtime

Pages cache their chunk results with Quarto freeze: auto; a page re-executes when its source changes. To force a full rebuild, delete _freeze/ and docs/. The heavy computation is not in the pages at all: it is in run_simulations.R, which took 7.9 minutes for the replications and 4 seconds for the control study and break-even on this run.

Known limits of reproducibility

  • Bit-for-bit equality is expected only on the same platform and package versions. Floating-point and BLAS differences across machines can change low-order digits, and occasionally the optimiser path of the Clark fits.
  • The mlReserve fork is a moving target on GitHub; the pinned commit keeps the experiment fixed, but the fork could disappear.
  • Quarto and Typst versions affect rendering, not the numbers.

Limitations and model risk

This project tests how estimation methods behave on data we generated. That is its strength (the true answer is known) and its main limitation (the answer holds only for this generator).

Key limitations

  1. Synthetic, uncalibrated parameters. Frequencies, lag distributions, severities and control effects are assumptions chosen for plausibility. Different values would change the numbers, and may change which method works.
  2. The generator and the methods share structure. Discovery lag is independent of origin period apart from the explicit scenarios, which is close to what chain-ladder assumes. Real loss databases have reporting-policy changes, system migrations and batch back-fills that create calendar-period effects the baseline does not contain.
  3. Loss is booked in full at discovery. Real events also have payment and recovery development after discovery. This is a second triangle layer that is not modelled.
  4. Event types are independent. In reality a market shock raises trade errors, NAV errors and unauthorized-position losses together.
  5. Control effects are assumed. The savings come from a posited link between time undiscovered and loss size, and an assumed shift in the lag distribution. We have no evidence for either magnitude.
  6. Frequency x severity ignores parameter uncertainty, so its intervals understate uncertainty by construction.
  7. Interval method. Mack and Clark intervals use a lognormal approximation to the total; the bootstrap uses empirical quantiles. Other choices would change coverage numbers somewhat.
  8. Annual vs. quarterly. Headline results use annual triangles because quarterly triangles are mostly unusable for the standard methods. A real firm with a long, dense history might do better at finer granularity.
  9. One firm size. A $5B stylised firm; no other sizes were tested.
  10. Poisson frequency, no clustering. Baseline counts are independent Poisson. Real operational-loss counts are overdispersed, and common-cause failures (for example a pricing feed that fails across many funds) produce batches of errors. The negative-binomial scenario adds overdispersion within an event type, but not clustering across types or across quarters.
  11. No reporting threshold in the baseline. Real loss databases only record losses above a collection threshold, often $10k to $20k. The median simulated trade error is about $2.4k, so a real database would hold far fewer trade errors. A $10k threshold is run as a sensitivity scenario.
  12. Some “method failures” are package limits, not method limits. ChainLadder::MackChainLadder() stops on triangles with empty development columns. Results with empty-column handling (factor 1) are reported next to the package results.
  13. Frequency x severity donor sparsity. At long lags few observed events exist, so severities are resampled from the few that do (or from all events when none are nearby, which drops the lag uplift). A variant that pools severities and re-applies an estimated uplift is reported.
  14. Every control result scales with the severity-growth parameter \(e\). With \(e = 0\) incurred loss is the same with and without the control (see Control Value).
  15. Pure IBNR only. Loss is booked in full at discovery, so there is no development on events already known (provisions, recoveries, insurance). The terminology here is IBNR, not IBNER.
  16. The benchmark development pattern is the generator’s own. The Bornhuetter-Ferguson variant with an external pattern shows what an accurate prior pattern buys; with a pattern that is itself wrong it would do worse, and the study does not test that.

What would change the conclusions

If we found… Effect
Real unauthorized-trading events are far more frequent than ~1 per year Standard methods become usable; the “cannot run” finding would weaken
Detection lags are stable over time in real data The control-improvement failure matters less in practice
Loss size does not grow with time undiscovered Control savings on expected loss largely disappear
Strong calendar-period effects in real data All development methods would need an explicit calendar term
Losses arrive in clusters from a common failure Chain-ladder variance is understated; Bornhuetter-Ferguson with a pooled pattern is preferred
Real collection threshold of $10k or more The trade-error triangle is mostly empty and the standard methods have little to work with

Use of the results

The numbers on this site are illustrations of method behaviour. They should not be quoted as estimates of any firm’s undiscovered losses or as a benchmark for the value of a particular control.
