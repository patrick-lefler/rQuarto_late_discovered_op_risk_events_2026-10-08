Results

How well can each method estimate the undiscovered loss? Every method is scored against the known truth on 200 simulated databases per scenario. Sections: summary, counts, dollar losses, validation across methods and stress tests. An experimental machine-learning comparator is on its own page because it does not feed the conclusions.

Summary by event type

For each event type, the method with the smallest absolute relative bias among methods that return a point estimate in at least 20 of 200 databases, the usable rate of the package Mack fit, and the best method that also supplies a 95% interval (so its coverage can be read).

Code 
elig <- sa |> filter(n_usable >= min_usable, !grepl("_tail$", method), !is.na(rel_bias))
pick <- \(d) d |> slice_min(abs(rel_bias), n = 1, by = type, with_ties = FALSE)
best_any <- elig |> pick()
best_int <- elig |> filter(has_interval) |> pick()
usable_mack <- sa |> filter(method == "mack") |> select(type, mack_usable = usable_rate)
best_any |>
  select(type, `Best point estimate` = method, `Rel. bias` = rel_bias, `Median signed rel. error` = median_rel_err) |>
  left_join(best_int |> select(type, `Best with interval` = method, `Bias (interval method)` = rel_bias, Coverage = coverage_usable), by = "type") |>
  left_join(usable_mack, by = "type") |>
  mutate(type = factor(type_lab[type], levels = type_lab),
         across(starts_with("Best"), \(x) method_lab[x])) |>
  arrange(type) |>
  rename(Type = type, `Package Mack usable` = mack_usable) |>
  gt::gt() |>
  gt::fmt_percent(c(`Rel. bias`, `Median signed rel. error`, `Bias (interval method)`, Coverage, `Package Mack usable`), decimals = 0) |>
  gt::sub_missing(missing_text = "-") |>
  gt::tab_source_note("Baseline, annual dollar triangles. 'Best' = smallest |relative bias|; this is a descriptive ranking on one simulator, and differences of a few percentage points are within simulation noise. For unauthorized trading the severity tail (shape 0.6) has infinite variance, so a few databases dominate every sum and the median signed error is the steadier statistic.")

How to read the table
Each row is an event type. The table names the method whose average estimate of the not-yet-found loss came closest to the true amount, and how often the range that method quotes actually contained the truth.

What the table tells you
For NAV errors a standard method lands within about 10% of the true missing loss, and for trade errors within about 1%, with its quoted range right roughly nine times in ten. For unauthorized trading, even the best method typically understates the missing loss by 29%, and its quoted range contains the truth only 63% of the time.

Count triangles

The first question is how many events are still undiscovered. The count triangle has the same shape as the amount triangle but each cell counts events, so it is free of the heavy-tailed severities that make amounts hard.

Code 
events <- simulate_database(params, rep = 1)
sq <- build_square(events, "nav_error", "count", 40, 40, period = 4)$square
plot_triangle(sq, "NAV errors: event counts by origin year and discovery lag", "Events")

How to read the plot
This is the same triangle as on the Overview page, but each box counts events instead of dollars. Each row is a year in which events happened, each column is how many years later they were found, and the fainter orange boxes are events not yet found.

What the plot tells you
The pattern is the same as for dollars: recent years show few recorded events only because many have not been found yet, so a raw count of recent events understates what has really happened.

Dollar-loss triangles

Dollar-loss triangles are what a risk committee cares about, but they are the hard case: a single large event dominates a cell, and late-discovered events are larger.

Routes to the missing amount

  1. Direct development methods on the dollar triangle: plain chain-ladder, Mack (the package implementation, and a version that sets development factors of empty columns to 1 so it runs on sparse triangles), Mack using only the latest three calendar diagonals, bootstrap chain-ladder, and Clark growth curves.
  2. Bornhuetter-Ferguson (BF) and Benktander. An a-priori expected loss (loss per unit exposure, estimated from the five oldest origin years, times exposure) is weighted by the share still unreported. The share comes either from the triangle’s own chain-ladder pattern, or from an external benchmark pattern. The benchmark here is the generator’s own lag distribution, so it shows what an accurate external pattern buys and is optimistic. BF and Benktander give point estimates only.
  3. Frequency x severity: project the number of undiscovered events from the count triangle, then price each projected event by resampling observed severities at a similar lag. This keeps the stable count signal separate from the noisy severities. It ignores parameter uncertainty, so we expect its intervals to be too narrow. A variant pools all observed severities and re-applies an estimated linear lag uplift.

Results (baseline, annual triangles, 200 simulated databases)

The target is the undiscovered loss inside the 10-year window. The one tail-extrapolating method (Clark with a tail) is scored against the total including loss beyond the window.

ts <- map_dbl(set_names(names(params$event_types)), \(t) tail_share(res$reps, t))
fs <- res$reps |>
  filter(method == "freq_x_sev", kind == "amount", granularity == "annual", scenario == "baseline") |>
  summarise(fallback = mean(fallback_share, na.rm = TRUE), min_donors = median(min_donors, na.rm = TRUE), .by = type)

  summarise(omega = median(fit_omega, na.rm = TRUE), theta = median(fit_theta, na.rm = TRUE), low_omega = mean(fit_omega < 0.2, na.rm = TRUE), .by = method)
cc <- cl_par |> filter(method == "clark_cc_weibull")
  • Trade and NAV errors: Mack, bootstrap, Bornhuetter-Ferguson and frequency x severity are all usable and within about 15% of the truth in aggregate. Relative biases for NAV errors are Mack 10%, bootstrap 14%, BF with its own pattern 7% and frequency x severity -7%.
  • Package Mack versus Mack with empty-column handling. The package fails in 200 of 200 unauthorized-trading databases (non-finite development factors from empty columns). Setting those factors to 1 makes it run in 200 of them, and identical to the package where the package runs (trade and NAV errors). So the failure is an implementation limit. But the result when it runs is poor: relative bias 866%, median signed error -42% and interval coverage 43%. A single large loss in the latest diagonal is multiplied by large factors, so the mean is far too high while the typical database is underestimated.
  • Bornhuetter-Ferguson on unauthorized trading does not remove the problem. With its own pattern the relative bias is 70% (median -15%); with the benchmark pattern 50% (median 14%). The a-priori loss per unit exposure is itself estimated from heavy-tailed history, so one large old loss inflates every origin year. BF has no interval here.
  • Frequency x severity has relative bias -4% on unauthorized trading and the best coverage among methods with intervals, but only 63%. At long lags few observed events exist: 62% of projected unauthorized-trading events are priced from the all-event pool because no events are nearby in lag (median fewest donors for any lag with projected events: 2). The uplift-pooling variant has relative bias 24% and coverage 67%, so pooling does not by itself fix the under-coverage.
  • Recent-origin bias (relative bias for the latest origin year only) is much larger than overall bias for unauthorized trading with frequency x severity (26% against -4% overall): the most recent origin year has the largest undiscovered share, so errors concentrate there, and it is exactly the year a decision-maker cares about.
  • Beyond the window: about 40% of the true undiscovered unauthorized-trading loss is discovered more than 40 quarters after origin, although only 2.7% of unauthorized-trading events are (late events are scaled up by the severity-growth term). No in-window method can see it; it needs an explicit tail assumption.

Method settings

  • Bootstrap: BootChainLadder with R = 1000 resamples and process.distr = "gamma". Re-running trade and NAV errors with "od.pois" on the first 100 databases gives practically the same bias and coverage, so this choice is not what drives the under-coverage.

How to read the table
The table compares two technical settings of the same bootstrap method on trade and NAV errors, showing average bias and how often its range contained the truth.

What the table tells you
The choice of setting makes no practical difference, so the bootstrap’s ranges being somewhat too narrow is not an artifact of how it was configured.

  • Clark curves: ages are period ends (1 to 10 years), the package default for the average date of loss (half an origin period), maxage is the window length, and Cape Cod exposure is the exposure path scaled so that expected loss ratios start near 1. These conventions are the package’s own; they are not the cause of the poor trade-error results. The cause is the shape of the data. About 100% of trade-error loglogistic fits end on the optimiser bound: the package restricts the loglogistic scale (the age by which half the loss is reported) to be at least half a year here, but most trade-error loss is already reported in the first period. The Weibull Cape Cod fit converges to a degenerate curve (median shape 0.09, scale 3.8 years) in 100% of trade-error databases, which implies a long thin tail that the oldest origin years do not show. That is a fit to the wrong shape, not exposure scaling, and the resulting 254% bias stands.

Method validation

Because the data are synthetic, every method can be scored against the true undiscovered amount. We generate 200 independent databases per scenario, fit each method to each, and record bias, error and interval coverage. A fit is usable only if the method ran and passed sanity checks. Fits that error out (failed) or return an implausible result (suspect, for example a bootstrap IBNR of zero, a bootstrap mean below 10% of the deterministic chain-ladder, or a growth-curve parameter on its optimiser bound) are excluded from bias figures. Two coverage columns are shown: coverage among usable fits, and coverage over all fits where failed, suspect and interval-free fits count as misses. Rows with fewer than 20 usable fits are shown as a dash.

These are tests of how methods behave under this simulator, not proof of how they behave on any real firm’s data.

Why fits fail

Code 
res$reps |>
  filter(scenario == "baseline", kind == "amount", granularity == "annual", status %in% c("failed", "suspect")) |>
  mutate(reason = case_when(
    grepl("NA/NaN/Inf", message) ~ "Package error: non-finite development factor (empty column)",
    grepl("optimiser bound", message) ~ "Growth-curve parameter at optimiser bound",
    grepl("bootstrap mean IBNR", message) ~ "Bootstrap returned ~0 where chain-ladder does not",
    grepl("zero", message) ~ "Bootstrap mean IBNR is zero",
    grepl("error in evaluating", message) ~ "Package error inside growth-curve fit",
    TRUE ~ substr(message, 1, 60)
  )) |>
  count(Type = factor(type_lab[type], levels = type_lab), Method = method_lab[method], Status = status, Reason = reason, name = "Fits") |>
  arrange(Type, desc(Fits)) |>

How to read the table
Each row counts how often a method failed or was flagged as unreliable, and the reason, for the baseline case.

What the table tells you
Failures are systematic, not random: they come from empty development columns in sparse data and from fitted curves that hit the limits of what the software allows. That is a warning that the data are too thin for the method, not a sign of a one-off error.

Reading the results

  • No method is reliable for every event type. The ranking changes with how many events there are and how heavy their tails are.
  • The standard development methods (Mack, bootstrap) are trustworthy where events are plentiful (trade errors) and acceptable where they are moderately frequent (NAV errors). Their intervals are somewhat too narrow even there.
  • For rare, heavy-tailed events (unauthorized trading), the package Mack cannot run, and once it is made to run it is badly biased with poor coverage. Bornhuetter-Ferguson with an external pattern and frequency x severity are the most defensible point estimates here, but all methods are unstable and none has well-calibrated intervals.

Stress tests

Chain-ladder methods assume that the pattern of past development carries forward. Five scenarios break that assumption, or the data-generating assumptions, in different ways. All use annual triangles and the same 200 seeds as the baseline (the scenario index is part of the seed, so each scenario has its own databases).

Scenario Why it is hard
Heavy-tail shock Two very large unauthorized-trading losses are injected; one is discovered, one is not yet (table below)
Control improvement Detection gets faster partway through, so history over-predicts future development
Exposure growth Rising volume distorts comparisons across origin periods
Overdispersion Negative-binomial counts (same mean as baseline, larger variance)
Reporting threshold $10k Losses below $10,000 are never recorded, as in many real loss databases

Heavy-tail shock: what is injected

Code 
n_o <- params$horizon$n_origin
inj <- load_params()$scenarios$heavy_tail_shock$injected_events
tibble(
  `Event` = seq_along(inj),
  `Origin quarter` = map_dbl(inj, "origin"),
  `Lag (quarters)` = map_dbl(inj, "lag"),
  `Discovery quarter` = `Origin quarter` + `Lag (quarters)`,
  Severity = map_dbl(inj, "severity")
) |>
  mutate(`Discovered by quarter 40?` = if_else(`Discovery quarter` <= n_o, "Yes (in the realised history)", "No (undiscovered at evaluation)")) |>

How to read the table
The table lists the two very large unauthorized-trading losses added to the stress scenario: when each happened, how long until discovery, and whether it was found by the end of the history.

What the table tells you
One loss was found inside the history and one was not: the second is discovered after the evaluation date, so it is part of the true undiscovered loss that no method could have seen in the data.

The undiscovered truth in this scenario is therefore mainly the second injected loss: it is not in the realised history, so a method cannot see it in the severity pool.

Control improvement: what the shift does

Code 
shift <- load_params()$scenarios$control_improvement$control_shift
cq <- shift$calendar_quarter
pairs <- map(1:40, \(r) {
  before <- simulate_database(apply_scenario(load_params(), "baseline"), rep = r) |> filter(type == "trade_error")
  set.seed(r)
  list(before = before, after = apply_control_shift(before, shift))
})
both <- \(f) c(Baseline = mean(map_dbl(pairs, \(p) f(p$before, p$before))), `After shift` = mean(map_dbl(pairs, \(p) f(p$before, p$after))))
# f(before, after) is evaluated on `after` and may use `before` to select the same events
rows <- list(
  "Mean lag, all events (quarters)" = both(\(b, e) mean(e$lag)),
  "Mean lag, events originating after the shift (quarters)" = both(\(b, e) mean(e$lag[b$origin > cq])),
  "Mean time remaining after the shift quarter, events pending at that quarter (quarters)" =
    both(\(b, e) mean((e$origin + e$lag - cq)[b$origin <= cq & b$origin + b$lag > cq])),
  "Share of events undiscovered at quarter 40" = both(\(b, e) mean(e$origin + e$lag > n_o))
)
tibble(Measure = names(rows), Baseline = map_dbl(rows, "Baseline"), `After shift` = map_dbl(rows, "After shift")) |>
  mutate(Change = `After shift` / Baseline - 1) |>
  gt::gt() |>
  gt::fmt_number(c(Baseline, `After shift`), decimals = 3) |>
  gt::fmt_percent(Change, decimals = 0) |>
  gt::tab_source_note("Trade errors, first 40 baseline databases, with the shift applied to the same events (paired). Time remaining is measured from the later of the shift quarter and the event's origin, and rounded stochastically.")

How to read the table
The table compares the same trade errors before and after the control improvement, showing how long they take to be found.

What the table tells you
The improvement does what it is meant to: events originating after it are found in about half the time, and the share of events still undiscovered at the end of the history falls by about half. This is the real change that the estimation methods are then asked to detect.

Mean estimate vs. mean truth

Relative errors explode when the true value is near zero, so this page shows absolute dollars: the mean undiscovered loss in the window, true and estimated, for the methods that run. Methods with fewer than 20 usable fits are omitted. “Mack, latest 3 diagonals” restricts development factors to the three most recent calendar diagonals, a standard remedy when development changes over calendar time; the “benchmark pattern” BF uses an externally supplied development pattern from the baseline generator, so it does not adapt to a changed pattern either.

Can a calendar-diagonal test see the change?

A simple diagnostic: the standardised age-to-age residuals on the latest two calendar diagonals, summed as a z-score. A strongly negative value means recent development is below what earlier years predicted. The table shows how often the test (z below -1.645) fires in each scenario.

Code

How to read the table
The table shows how often a simple alarm, which compares the latest two years of development with earlier years, signals that detection has changed.

What the table tells you
The alarm rarely fires when nothing has changed, but it also catches the real control improvement in only 32% of trade-error databases and 12% of NAV-error databases. A firm should not wait for a statistical alarm before checking whether an improved control has changed its loss pattern.

What the stress tests show

  • Control improvement. After detection speeds up, the true undiscovered trade-error amount falls from $185.0K to $94.5K, about half. Methods trained on the earlier, slower history keep projecting the old development: Mack’s mean estimate is $153.4K, 62% too high. A firm that has just improved its controls will over-reserve if it applies old development factors. Restricting the factors to the latest three diagonals removes most of the error here ($96.2K against the truth) and reduces it for NAV errors ($2.1M against $1.6M), at the price of noisier factors in the other scenarios (4% bias and 88% coverage for trade errors in the baseline, against 1% and 94%). It does not help unauthorized trading. The calendar-diagonal test is weak on 10 x 10 annual triangles: it flags the change in 32% of trade-error databases and 12% of NAV-error databases, against about 0% false alarms in the baseline. A change that the test cannot see on annual data can still be large enough to matter.
  • Heavy-tail shock. For unauthorized trading, frequency x severity has relative bias -33% and interval coverage 94%. BF with a benchmark pattern is close in aggregate (11%), and plain chain-ladder is wildly high because the injected losses are multiplied by large development factors. One injected loss is discovered inside the realised history and one is not (table above), so part of the truth is information the severity pool never contained.
  • Exposure growth. Moderate growth changes little for the event types where the methods already work.
  • Overdispersion. Interval coverage falls for the methods that have intervals: Mack covers 90% of trade-error databases and bootstrap 78%, against 94% and 86% in the baseline. Clustered or overdispersed counts make the stated 95% intervals less trustworthy.
  • Reporting threshold. A $10k threshold removes most trade errors from the database (the true undiscovered trade-error amount falls from $185.0K to $80.0K) while NAV errors and unauthorized trading are barely affected; for trade and NAV errors the standard methods still work on what remains (unauthorized-trading means are dominated by a few databases and vary a lot between scenarios).
