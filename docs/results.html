Results

How well can each method estimate the undiscovered loss? Every method is scored against the known truth on 200 simulated databases per scenario. Sections: counts, dollar losses, validation across methods, stress tests and an experimental machine-learning comparator.

Count triangles

The first question is how many events are still undiscovered. The count triangle has the same shape as the amount triangle but each cell counts events, so it is free of the heavy-tailed severities that make amounts hard.

Code 
events <- simulate_database(params, rep = 1)
sq <- build_square(events, "nav_error", "count", 40, 40, period = 4)$square
plot_triangle(sq, "NAV errors: event counts by origin year and discovery lag", "Events")

  • Trade errors (many events, fast discovery): Mack and Bootstrap are close to unbiased (relative bias 1% and 1%).
  • NAV errors: Mack relative bias 4%, interval coverage 96%.
  • Unauthorized trading (about one event a year): Mack is usable in 0 of 200 databases. With so few events, a count triangle has too little data for development factors; the chain-ladder point estimate is available but has no interval.

Quarterly triangles (40 x 40) are far sparser; see Method validation for the usable-fit rates.

Dollar-loss triangles

Dollar-loss triangles are what a risk committee cares about, but they are the hard case: a single large event dominates a cell, and late-discovered events are larger.

Two routes to the missing amount

  1. Direct: run the development methods on the dollar triangle (Mack, Bootstrap, Clark LDF, Clark Cape Cod, plain chain-ladder).
  2. Frequency x severity: project the number of undiscovered events from the count triangle, then price each projected event by resampling observed severities at a similar discovery lag. This keeps the stable count signal separate from the noisy severities. It ignores parameter uncertainty, so we expect its intervals to be too narrow.

  • Trade and NAV errors: Mack, Bootstrap and frequency x severity are all usable. Relative biases for NAV errors are Mack 10%, Bootstrap 14% and frequency x severity -7%.
  • Clark curves are unreliable here. The loglogistic fit is usable in 0 of 200 trade-error databases. Where most loss is discovered in the first period, the fitted growth curve sits on an optimiser bound and extrapolates badly.
  • Unauthorized trading: only the plain chain-ladder point estimate and frequency x severity produce a result in most databases. The chain-ladder estimate is wildly unstable (relative bias 866%, median error -42%), because a single large loss in the latest diagonal is multiplied by large development factors. Frequency x severity has relative bias -4% but its interval covers the truth only 63% of the time.
  • Beyond the window: about 40% of the true undiscovered unauthorized-trading loss is discovered more than 40 quarters after origin. No in-window method can see it; it needs an explicit tail assumption.

Method validation

Because the data are synthetic, every method can be scored against the true undiscovered amount. We generate 200 independent databases per scenario, fit each method to each, and record bias, error and interval coverage. A fit is usable only if the method ran and passed sanity checks; fits that error out (failed) or return an implausible result (suspect, for example a bootstrap IBNR of zero when a deterministic chain-ladder says otherwise) are excluded from bias figures and counted as misses for coverage.

These are tests of how methods behave under this simulator, not proof of how they behave on any real firm’s data.

Reading the results

  • No method is reliable for every event type. The ranking changes with how many events there are and how heavy their tails are.
  • The standard development methods (Mack, Bootstrap) are trustworthy where events are plentiful (trade errors) and acceptable where they are moderately frequent (NAV errors). Their intervals are somewhat too narrow even there.
  • For rare, heavy-tailed events (unauthorized trading), the standard methods mostly cannot run, and the ones that do are unstable. A frequency-severity decomposition gives a usable but overconfident answer.

Stress tests

Chain-ladder methods assume that the pattern of past development carries forward. Three scenarios break that assumption in different ways. All use annual triangles and the same 200 seeds as the baseline.

Scenario Why it is hard
Heavy-tail shock Two very large unauthorized-trading losses sit inside the window
Control improvement Detection gets faster partway through, so history over-predicts future development
Exposure growth Rising volume distorts comparisons across origin periods

Mean estimate vs. mean truth

What the stress tests show

  • Control improvement. After detection speeds up, the true undiscovered amount shrinks to near zero but methods trained on the earlier, slower history still project substantial development. For trade errors Mack’s mean estimate is $116.14K against a true $616. In practice this means a firm that has just improved its controls will over-reserve if it applies old development factors, and a development method cannot tell a real improvement from noise without a change-point test.
  • Heavy-tail shock. For unauthorized trading, frequency x severity has relative bias -33% and interval coverage 94% in this scenario. The injected losses are in the realised history, so the method sees them in the severity pool; whether a future shock is anticipated is a different question that this design does not test.
  • Exposure growth. Moderate growth changes little for the event types where the methods already work.

Experimental: ML reserving

WarningExperimental, excluded from headline results

mlReserve() comes from a personal fork of the ChainLadder package (thierrymoudiki/ChainLadder, pinned to commit 30cc7a84, package version 0.2.22), not from CRAN. Its published evidence is a blog post using simulated insurance triangles. It was installed into an isolated library so the CRAN ChainLadder used on every other page is unaffected. Nothing on this page feeds the executive summary.

What it does

mlReserve() fits a machine-learning regression (here a random forest from ranger or a support vector machine from e1071) to the observed cells of a triangle, using origin and development period as features, and predicts the unobserved cells. It is a different idea from chain-ladder’s multiplicative development factors.

The test

Same simulated databases as the baseline validation (replications 1-30), annual dollar triangles, scored on the undiscovered loss inside the window. Four configurations are run and all are reported; none was chosen using the true values. The first is the setting used in the blog post. Point estimates only (no bootstrap intervals).

Reading the result

  • Every mlReserve configuration overestimates on the two event types where classical methods work. For NAV errors the closest configuration (mlReserve: rf_raw_both) has a median estimate/truth ratio of 3, against 0.84 for Mack. For trade errors the closest (mlReserve: rf_raw_both) is 20x the truth, against 0.96 for Mack.
  • Why: on a single triangle, the learner extrapolates an upward trend across origin years into cells that, in this simulator, are nearly fully developed. With 10 origin years there are only 55 training cells and tree/kernel learners have no development-factor structure to anchor them.
  • The blog’s asinh transform, applied to dollar values, gives a median ratio of 31 for trade errors, worse than the same learner with no transform in the cases we ran; it may be calibrated for much smaller numeric scales, and we did not test rescaling the data first.
  • Unauthorized trading: the closest configuration (mlReserve: svm_raw_numeric, median ratio 1.3) is not a useful comparison either way, since the truth is small and the estimates are highly dispersed.
  • We report the configurations after the fact for transparency; none was selected using the truth, and “closest” above describes this experiment, not a recommendation.

Taken together, this is a limited test, on one data-generating process, with no tuning, of an unreleased fork. It gives no support for using mlReserve here, and it does not show that the approach cannot work with more data or tuning.
